manage.py làm gì, và request đi về đâu

manage.py — file bạn gõ liên tục (uv run python manage.py ...) — thực ra làm gì? Và Django biết chạy code nào khi có request tới nhờ đâu?

1. if __name__ == "__main__": — idiom mới, chưa gặp ở bài 1–7

# manage.py
def main():
    ...

if __name__ == "__main__":
    main()

__name__ là biến string Python tự động gán cho mọi module khi nạp. Giá trị phụ thuộc vào cách file được chạy:

  • Nếu file được chạy trực tiếp bằng python manage.py ..., Python đặt __name__ = "__main__" cho chính file đó.
  • Nếu file bị import từ file khác (ví dụ import manage), Python đặt __name__ bằng tên module — ở đây là "manage" — chứ không phải "__main__".
Ví dụ minh hoạ: giả sử có file b.py: 
# b.py
print("giá trị __name__ của b.py là:", __name__)
và file a.py: 
# a.py
import b
  • Chạy python b.py trực tiếp → in ra giá trị __name__ của b.py là: __main__.
  • Chạy python a.py (import b từ a) → in ra giá trị __name__ của b.py là: b — vì lúc này b.py không phải file khởi động, nó chỉ là module bị mượn code.
Cùng một file, cùng một dòng print, nhưng __name__ khác nhau tuỳ cách file được gọi.

if __name__ == "__main__": main() nghĩa là: chỉ tự chạy main() khi file được chạy trực tiếp, không chạy khi bị import để tái sử dụng.

Node.js

Gần nhất là require.main === module (CommonJS) — cùng ý tưởng, khác cú pháp.

Python

Cơ chế có sẵn, không cần import gì thêm — idiom phổ biến ở cuối gần như mọi script chạy độc lập.

2. manage.py thật sự làm 3 việc

Nội dung thật của manage.py trong be-py-eco (đã lược comment/docstring):

SRC_DIR = Path(__file__).resolve().parent / "src"

def main():
    sys.path.insert(0, str(SRC_DIR))
    os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings.local")
    try:
        from django.core.management import execute_from_command_line
    except ImportError as exc:
        raise ImportError(...) from exc
    execute_from_command_line(sys.argv)

if __name__ == "__main__":
    main()
  1. sys.path.insert(0, str(SRC_DIR)): thêm src/ vào đầu đường dẫn tìm module, để import config... hoạt động.
  2. os.environ.setdefault(...): chỉ đặt biến môi trường này khi chưa tồn tại — không ghi đè nếu bạn đã tự set (ví dụ cho staging).
  3. execute_from_command_line(sys.argv): chuyển toàn bộ tham số dòng lệnh cho Django xử lý — cùng một file phục vụ mọi lệnh (migrate, runserver, ...).

try/except ImportError quanh việc import Django: nếu Django chưa cài, ném lại thông báo rõ ràng thay vì lỗi khó hiểu mặc định.

3. urls.py: bản đồ URL → hàm xử lý (view)

Khi request HTTP tới, Django tra urlpatterns — danh sách cặp (URL, view) do bạn khai báo — để biết chạy code nào. Cú pháp tổng quát (ví dụ minh hoạ, không phải code hiện có trong be-py-eco):

from django.urls import path
urlpatterns = [
    path("health/", health_check_view),
    path("api/v1/orders/", order_list_view),
]

Mỗi path(...) ghép một URL với một view — hàm/class chạy khi request khớp URL đó, thay cho if/else so khớp thủ công.

Nội dung thật của src/config/urls.py trong be-py-eco hiện tại: 
"""URL configuration for the be-py-eco project.

Empty for now — the `/api/v1/...` namespace and `/health/*` endpoints land
in Slice 1 (see Issue #5's "Explicit non-decisions" section).
"""

from django.urls import URLPattern, URLResolver

urlpatterns: list[URLPattern | URLResolver] = []
urlpatterns đang rỗng — có chủ đích: dự án ở Slice 0, route /api/v1/... và /health/* sẽ thêm ở Slice 1 (xem Issue #5). Type hint list[URLPattern | URLResolver]: mỗi phần tử phải là URLPattern (từ path(...)) hoặc URLResolver (khi include URL con) — giúp editor/mypy bắt lỗi sớm, không ảnh hưởng lúc chạy.

4. Vì sao tách manage.py và urls.py ra hai việc khác nhau?

manage.py là điểm vào dòng lệnh — chạy một lần rồi thoát. urls.py là cấu hình định tuyến — Django nạp và giữ suốt thời gian server chạy. Hai file không gọi trực tiếp lẫn nhau: Django tự tìm đến urls.py qua DJANGO_SETTINGS_MODULE → ROOT_URLCONF. Mỗi file một trách nhiệm rõ ràng.
