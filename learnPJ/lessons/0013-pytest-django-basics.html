Test trong be-py-eco: đọc code test thật, không phải ví dụ giả

Bài này dùng 2 file test thật trong repo — tests/common/test_ids.py và tests/test_environment.py. Trọng tâm: đọc hiểu output khi test fail, vì đó là việc bạn làm thường xuyên hơn viết test mới.

1. Test chỉ là hàm bắt đầu bằng test_

# tests/common/test_ids.py
import uuid
from common.ids import uuid7

def test_uuid7_returns_valid_uuid():
    value = uuid7()
    assert isinstance(value, uuid.UUID)
    assert value.version == 7

pytest tự quét file test_*.py, tìm hàm test_* và chạy từng hàm độc lập: không lỗi thì PASS, có exception (kể cả từ assert) thì FAIL. Không cần đăng ký test ở đâu cả.

pytest dùng assert thường (không cần assertEqual như unittest) vì nó "viết lại" câu lệnh này lúc import, để khi fail in ra giá trị thật của từng biến. Ví dụ nếu uuid7() bị sửa hỏng version, chạy lại test sẽ thấy:

tests/common/test_ids.py:9: in test_uuid7_returns_valid_uuid
    assert value.version == 7
AssertionError: assert 4 == 7
 +  where 4 = UUID('...').version

======================== 1 failed, 2 passed in 0.08s ========================

Dòng 1 là file:dòng gây lỗi, dòng 3 là giá trị pytest "bung" ra (4 == 7), dòng cuối tóm tắt số pass/fail. Quen đọc 3 dòng này quan trọng hơn nhớ cú pháp assert.

2. Test đụng tới database cần đánh dấu tường minh

# tests/test_environment.py
import pytest
from django.db import connection

@pytest.mark.django_db
def test_database_connection_is_reachable():
    connection.ensure_connection()
    assert connection.is_usable()
@pytest.mark.django_db — nhận ra chứ? Lại là decorator (bài 7), nhưng ở đây nó không bọc hàm để thêm logic, mà chỉ gắn một "nhãn" (marker) để pytest-django biết hàm này được phép chạm database. Thiếu nhãn này, hàm vẫn chạy — nhưng ngay dòng đầu tiên chạm tới DB sẽ ném lỗi: 
Failed: Database access not allowed, use the "django_db" mark,
or the "db" or "django_db" fixture to enable it.
pytest-django cố tình chặn DB theo mặc định, để nhìn marker là biết ngay test nào cần DB (chậm) và test nào không (nhanh), không cần chạy thử.

3. Vì sao mỗi test không cần tự dọn dữ liệu

Dữ liệu test trước có còn tồn tại khi test sau chạy không? Không — mỗi hàm test được bọc trong một database transaction: pytest-django mở transaction trước khi chạy, rồi ROLLBACK sau khi chạy xong (dù pass hay fail), thay vì COMMIT.

Vì vậy bạn không cần code dọn dẹp (không tearDown) và các test có thể chạy thứ tự bất kỳ, thậm chí song song. Cái giá: không thể dùng test để kiểm tra hành vi xuyên nhiều transaction thật — trường hợp đó cần fixture khác (transactional_db), ngoài phạm vi bài này.

be-py-eco dùng Postgres thật thay vì SQLite (xem guild.md §10.5) để tránh khác biệt hành vi giữa hai database.

4. Chạy test — bạn đã dùng những lệnh này từ how-to-run.md

uv run python -m pytest
uv run python -m pytest tests/common/test_ids.py
uv run python -m pytest tests/common/test_ids.py::test_uuid7_returns_valid_uuid

Cú pháp file.py::ten_ham chạy đúng 1 test: pytest map "địa chỉ" (file + tên hàm) tới đúng hàm đó rồi gọi.

Thêm -x để dừng ngay ở test fail đầu tiên, hoặc -v để in tên từng test — hữu ích khi debug suite lớn.

5. Fixture: setup dùng chung, tiêm qua tên tham số

# tests/conftest.py
import pytest

@pytest.fixture
def sample_book():
    return Book.objects.create(title="Chi Pheo", author="Nam Cao")

def test_book_is_available_by_default(sample_book):
    assert sample_book.available is True

Tham số sample_book trùng tên với fixture — pytest tự "tiêm" giá trị vào (dependency injection theo tên), không cần gọi tay hay import. Vì fixture này chạm DB, hàm test dùng nó cũng cần @pytest.mark.django_db.

Đặt trong conftest.py nghĩa là mọi file test cùng thư mục (và thư mục con) dùng được fixture này mà không cần import.

6. Parametrize: chạy 1 hàm test với nhiều bộ dữ liệu

Khi muốn kiểm tra cùng một hành vi với nhiều input khác nhau, viết nhiều hàm test_... gần giống hệt nhau là dư thừa. @pytest.mark.parametrize cho phép khai báo một lần, pytest tự sinh nhiều test case:

import pytest

@pytest.mark.parametrize("value,expected", [
    (1, "one"),
    (2, "two"),
    (3, "three"),
])
def test_number_to_word(value, expected):
    assert number_to_word(value) == expected

pytest chạy hàm này 3 lần, báo cáo riêng từng lần — nếu case 2 fail, output ghi rõ test_number_to_word[2-two] fail, 2 case kia vẫn pass.

Tài liệu tra cứu đầy đủ: Cheat sheet pytest-django Basics. Nguồn chính nên đọc song song: pytest-django docs và pytest docs — Fixtures.
