Bài 16 · Django/DRF nâng cao (be-py-eco)

Hai lớp permission: view lọc loại actor, service lọc quyền cụ thể

Bài 15 đã có request.user đúng loại (Customer/Staff). Bài này trả lời câu tiếp theo: Staff đó có được phép gọi hành động này không — và vì sao câu trả lời không nằm trong view.

1. Anti-pattern quen thuộc: rải role-check trong view

Cách hay gặp

def post(self, request):
    if request.user.role != "admin":
        return Response(403)
    # ...logic thuc su...

be-py-eco

def post(self, request):
    staff = request.user
    create_staff(actor=staff, ...)
    # check quyen nam trong service,
    # khong nam trong view nay

Rải if user.role == ... trong từng view khiến quy tắc phân quyền tản mát khắp codebase — sửa 1 quy tắc phải tìm đúng từng view. OWASP gọi đây là thiếu centralized authorization.

2. Lớp 1 (view): IsStaff — chỉ lọc loại actor

JWTAuthentication (bài 15) xác thực cả Customer và Staff — IsAuthenticated không phân biệt được 2 loại này. Cần thêm permission riêng:

class IsStaff(BasePermission):
    def has_permission(self, request, view):
        return isinstance(request.user, Staff)
IsStaff chỉ trả lời "đây có phải nhân viên không?" — nó không biết nhân viên này có role gì, càng không biết role đó có được phép create_staff hay không. Đó là việc của lớp thứ hai.

3. Lớp 2 (service): ROLE_PERMISSIONS — một dict, một nguồn sự thật

MASTER_ADMIN = "master_admin"
STORE_MANAGER = "store_manager"
ORDER_STAFF = "order_staff"

ROLE_PERMISSIONS = {
    MASTER_ADMIN: {
        "accounts.create_staff",
        "accounts.disable_customer",
        "accounts.reset_staff_mfa",
    },
    STORE_MANAGER: {"accounts.disable_customer"},
    ORDER_STAFF: set(),
}

Mỗi hành động nhạy cảm có một "codename" riêng (giống accounts.create_staff) — mọi module tự thêm codename của mình vào đây khi cần, không sửa logic ở nơi khác.

4. check_policy(): quyền thô + policy theo từng object

def has_permission(role, codename):
    return codename in ROLE_PERMISSIONS.get(role, set())

def check_policy(*, role, codename, obj=None, object_check=None):
    if not has_permission(role, codename):
        return False
    return object_check(obj) if object_check is not None else True

object_check là callback tùy chọn — cho phép hỏi thêm câu thứ hai sau khi đã qua quyền thô: "role này được phép codename nói chung, nhưng còn object cụ thể này thì sao?" (ví dụ tương lai: Order Staff chỉ được xử lý đơn hàng được giao cho chính họ, không phải mọi đơn hàng trong hệ thống).

5. Service tự raise lỗi — view không biết gì về "role"

CREATE_STAFF_CODENAME = "accounts.create_staff"

def create_staff(*, actor, email, password, role, request=None):
    if not check_policy(role=actor.role, codename=CREATE_STAFF_CODENAME):
        raise InsufficientPermissionError
    require_confirmed_mfa(actor)
    # ...logic tao Staff thuc su...

InsufficientPermissionError được bài 1 của PR #19 (chưa học tới) chuyển thành response 403 kiểu Problem Details — view chỉ gọi create_staff(...), không hề biết "quyền" nghĩa là gì.
