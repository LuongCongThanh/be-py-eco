Bài 15 · Django/DRF nâng cao (be-py-eco)

Một JWT, hai loại actor — vì sao PR #19 không dùng AUTH_USER_MODEL

Bài 9-12 đã dùng Django "mặc định" (settings, ORM, DRF views cơ bản). PR #19 (Slice 1: Accounts) lại không dùng AUTH_USER_MODEL của Django cho khách hàng/nhân viên — bài này giải thích quyết định đó và cách JWT tự chế thay thế nó.

1. Django "mặc định" làm gì, be-py-eco làm khác gì

Django mặc định

class User(AbstractUser):
    ...

request.user  # instance cua
# AUTH_USER_MODEL, 1 bang duy nhat

be-py-eco

class Customer(BaseModel): ...
class Staff(BaseModel): ...
# 2 bang rieng, khong ke thua
# AbstractUser/AbstractBaseUser

Customer (khách mua hàng) và Staff (nhân viên nội bộ) là hai loại actor rất khác nhau: đăng nhập khác (mật khẩu/Google vs. bắt buộc MFA), thời hạn token khác. Gộp chung một bảng AUTH_USER_MODEL sẽ phải nhồi cả hai logic vào một model.

2. Vậy request.user là gì, nếu không phải AUTH_USER_MODEL?

Vẫn là JWT (access/refresh token) như DRF hay dùng — chỉ khác ở một claim thêm vào token: actor_type, ghi rõ token này của "customer" hay "staff".

ACTOR_TYPE_CLAIM = "actor_type"
CUSTOMER_ACTOR_TYPE = "customer"
STAFF_ACTOR_TYPE = "staff"

refresh = RefreshToken.for_user(customer)
refresh[ACTOR_TYPE_CLAIM] = CUSTOMER_ACTOR_TYPE
refresh.access_token[ACTOR_TYPE_CLAIM] = CUSTOMER_ACTOR_TYPE
RefreshToken.for_user() là hàm gốc của thư viện simplejwt — nó không quan tâm customer có phải AUTH_USER_MODEL hay không, chỉ cần object có thuộc tính id để nhét vào claim user_id của token.

3. Dispatch: get_user() tự tra đúng bảng

Mặc định, simplejwt tra request.user bằng cách query một bảng AUTH_USER_MODEL cố định. PR #19 override lại get_user() để tự chọn bảng dựa vào actor_type đọc từ token:

class JWTAuthentication(BaseJWTAuthentication):
    def get_user(self, validated_token):
        actor_type = validated_token.get(ACTOR_TYPE_CLAIM)
        actor_id = validated_token.get(api_settings.USER_ID_CLAIM)

        if actor_type == CUSTOMER_ACTOR_TYPE:
            return Customer.objects.get(id=actor_id, is_active=True)

        if actor_type == STAFF_ACTOR_TYPE:
            return Staff.objects.get(id=actor_id, is_active=True)

        raise InvalidToken("Token is missing a recognized actor_type claim.")

Đây chính là duck typing (bài 5) ở tầm framework: DRF gọi request.user không quan tâm nó là Customer hay Staff, chỉ cần object trả về đúng "hình dạng" DRF cần.

4. "Hình dạng" DRF cần: is_authenticated, is_anonymous

IsAuthenticated của DRF chỉ gọi request.user.is_authenticated — không kiểm tra type. Vì Customer không kế thừa AbstractBaseUser (thứ vốn có sẵn 2 thuộc tính này), model phải tự khai báo shim:

class Customer(BaseModel):
    email = models.EmailField(unique=True)
    ...

    @property
    def is_authenticated(self):
        return True    # da qua get_user() thanh cong = coi nhu authenticated

    @property
    def is_anonymous(self):
        return False

Không có 2 property này, IsAuthenticated sẽ AttributeError ngay khi kiểm tra — dù JWT hợp lệ và get_user() đã trả về đúng Customer.

5. Staff sống ngắn hơn Customer — cùng cơ chế, khác cấu hình

Access/refresh token của Customer dùng thời hạn mặc định trong settings.py:

SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=15),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=30),
}

Staff cần ngắn hơn (rủi ro cao hơn nếu lộ token) — thay vì thêm if vào get_user(), PR #19 subclass riêng 2 class token, chỉ đổi lifetime:

class StaffAccessToken(AccessToken):
    lifetime = timedelta(minutes=10)   # thay vi 15 phut cua Customer

class StaffRefreshToken(RefreshToken):
    lifetime = timedelta(days=7)        # thay vi 30 ngay cua Customer
    access_token_class = StaffAccessToken

6. Toàn cảnh: một request đi qua đâu

Claim actor_type sai hoặc thiếu (token giả mạo, hoặc bảng cũ chưa có claim này) → InvalidToken ngay, không rơi vào nhánh nào — không có actor "mặc định" nào cả.
