Model: class Python biến thành table database

Lưu ý: src/modules/ trong be-py-eco hiện đang rỗng — dự án ở Slice 0, chưa có model nghiệp vụ nào. Bài này dạy khái niệm ORM tổng quát của Django (áp dụng cho bất kỳ project Django nào), không phải đọc lại code có sẵn trong repo như các bài 9–10.

1. Vì sao Django cần "model" thay vì viết SQL tay?

Django dùng một quy ước: 1 class Python = 1 table, 1 attribute = 1 cột, 1 instance = 1 dòng dữ liệu — bạn thao tác object Python bình thường, Django lo phần dịch sang SQL.

2. Model = 1 class kế thừa models.Model

from django.db import models

class Author(models.Model):
    name = models.CharField(max_length=200)

class Book(models.Model):
    title = models.CharField(max_length=200)
    pages = models.IntegerField()
    available = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)
    author = models.ForeignKey(Author, on_delete=models.CASCADE)

class Book(models.Model): là kế thừa bạn học ở bài 4 — models.Model cho Book toàn bộ hành vi lưu/truy vấn database (.save(), .delete()).

Mỗi thuộc tính class là một cột, kiểu field quyết định kiểu cột thật trong Postgres:

  • CharField(max_length=200) — chuỗi ngắn, bắt buộc khai báo độ dài tối đa (khác TextField không giới hạn).
  • IntegerField() — số nguyên.
  • BooleanField(default=True) — true/false.
  • DateTimeField(auto_now_add=True) — thời điểm tạo, Django tự điền.

Field author = models.ForeignKey(Author, on_delete=models.CASCADE) khai báo quan hệ 1-nhiều: Django tạo cột author_id trỏ tới bảng Author; on_delete=models.CASCADE nghĩa là xoá Author thì các Book liên quan bị xoá theo.

3. Migration: đồng bộ code Python ↔ schema thật trong Postgres

Model chỉ là code Python — chưa tạo table nào cả. Cần 2 lệnh tách biệt để sinh và áp schema thật:

uv run python manage.py makemigrations
uv run python manage.py migrate

makemigrations chỉ sinh file mô tả thay đổi (để review/commit trước) — migrate mới thật sự chạy CREATE TABLE/ALTER TABLE lên Postgres. Bạn đã chạy migrate khi setup project (xem how-to-run.md).

4. QuerySet: method chain thay cho viết SQL tay

Book.objects.all()
Book.objects.filter(available=True)
Book.objects.filter(author__name="Nam Cao").first()
Book.objects.get(id=some_id)

Book.objects là điểm vào để xây câu truy vấn; .filter() trả về QuerySet mới nên có thể chain tiếp (builder pattern). Cú pháp author__name="Nam Cao" (hai dấu gạch dưới) là cách Django "băng qua" ForeignKey để lọc theo field của bảng liên quan.

5. QuerySet "lười" (lazy) — chỉ chạy SQL khi thật sự cần

Đây là điểm khác biệt lớn nhất so với tự viết SQL, và cũng là chỗ dễ gây bug nếu không hiểu rõ:

qs = Book.objects.filter(available=True)
# Dòng trên: CHUA co SQL nao duoc gui di.
# Django chi ghi nho "yeu cau" nay vao object qs, giong nhu viet ra
# 1 cong thuc nhung chua bam nut tinh.

qs = qs.exclude(pages__lt=50)
# Van CHUA chay SQL. Day chi la ghep them dieu kien vao cong thuc,
# tra ve 1 QuerySet moi (khong sua doi qs cu).

for book in qs:
    # SQL THUC SU duoc gui toi Postgres NGAY TAI DAY, khi vong for
    # bat dau lay phan tu dau tien. Ket qua duoc Django cache lai
    # trong qs cho cac lan lap sau (khong query lai).
    print(book.title)
Vì sao "lười"? Vì hiệu năng — thay vì bắn 1 câu SQL riêng cho mỗi .filter()/.exclude(), Django gộp tất cả điều kiện thành đúng 1 câu SQL, chạy đúng 1 lần khi bạn thật sự cần dữ liệu.
